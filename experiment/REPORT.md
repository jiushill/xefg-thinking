# XeFG 思考插件 A/B 实验报告

日期：2026-11-03 / 目标：`${VM_HOST:-192.0.2.10}` (Ubuntu 24.04, Docker)

## 1. 靶场

- 8 个 pwn 二进制（`D:\download\pentest`，4 个 zip + 4 个裸 ELF），已解包并统一命名到
  `~/pwnrange/chals/{a1..a4,b1..b4}/`。
- 镜像 `xefg/range:1`，基础 `debian:bookworm`。**离线构建**：该 VM 的容器网络到不了任何包源
  （`docker build` 里的 `apt-get update` 会挂死），所以 socat (Debian bookworm 构建) + 其依赖
  库 + 32 位 loader/libc 都是从宿主机取包后以 payload 形式 COPY 进镜像的。
  踩坑：Debian 12 是 merged-usr，`/lib` 是指向 `usr/lib` 的符号链接，`COPY payload/lib/ /lib/`
  会把链接替换成真目录，导致 `/lib64/ld-linux-x86-64.so.2` 断裂、`/bin/sh` 无法 exec。
  改成显式目标路径后正常。
- 一题一容器，`--network host`，端口 10001–10008，`socat TCP-LISTEN:$PORT,reuseaddr,fork EXEC:$BIN,pty,rawer`。
  每个容器内 `/flag` 内容不同（`XEFG{<id>-<12hex>}`）。
- 32 位题（b1 动态 / b4 静态）能在容器里跑，靠的是 host 的 i386 运行时被一并打进镜像。
- 连通性：8/8 端口各连续 3 次连接全部成功。

## 2. 实验设计

4 题 × 4 阶段，同一份提示词模板（只有 challenge id / port / 二进制路径不同），每条 subagent
全新上下文、并行开跑、10 分钟上限。我作为调度方只做：切插件挡位、发同一份 brief、复验 flag。

| 阶段 | 插件状态 | 参数 |
|---|---|---|
| P0 | 关闭（基线） | — |
| P1 | 开启 · 默认挡 | holeMax .25 / tauFlow .45 / strict off |
| P2 | 开启 · 严格挡 | holeMax .20 / tauFlow .55 / weakAsHole on |
| P3 | 开启 · 默认挡 + 强制调用 | 同 P1，brief 追加"每个假设链必须调用 xefg_frame 并按其裁决行动"，仅 2 题 |

工程控制：
- `run.sh` 只按**模式**匹配 `XEFG{...}`，flag 明文不落在 VM 上（`$HOME` 下无任何 flag 文本）。
- 每阶段结束后把 `~/pwnrange/solves/pN` 移到 `/root/pN-solves`（700），下一阶段读不到上一阶段的解。
- 用户态 sudo 通过一次性 askpass 完成，用完即删。
- 所有 flag 由我本地 `vm/flags-local.txt` 逐字复验，不采信 subagent 自述。

## 3. 结果

耗时 = 从阶段 T0 到该题在服务上打出 flag 的那次运行（秒）。

| 题 | 漏洞类型 | P0 关闭 | P1 默认 | P2 严格 | P3 默认+强制 |
|---|---|---|---|---|---|
| a1 | scanf 溢出 + ret2backdoor | **18** | 40 | 38 | — |
| b2 | read 溢出 + ret2win (callsystem) | **18** | 40 | 82 | — |
| a4 | 格式化串泄 canary + ret2backdoor | **48** | 129 | 50 | 74 |
| b1 | 32 位 ret2dlresolve | 235 | **78** | 231 | 86 |
| 整段 makespan | | 235 | **129** | 231 | — |
| 四题总和 | | 319 | 287 | 401 | — |
| `xefg_frame` 调用次数 | | 0 | **0** | **0** | **4** |

成功率：12/12 全部拿到 flag，逐字复验通过。没有一次失败。

## 4. 结论

**没测出加速。而且主要原因是机制没被触发。**

1. **未强制时工具零调用。** P0/P1/P2 三个阶段 12 次解题，`xefg_frame` 调用次数为 0。
   原因不是工具缺失——我直接问过 P1 的 a1 agent，它确认 `xefg_frame` / `xefg_verify` 都在工具列表里、
   系统提示里也有完整协议段。是协议自身写了"链长超过 4 个单元才调用"，而这几题的本质是
   *一个 bug + 一个原语*，推理跨度只有 1–3 个单元，于是每次跳过都是合规的。
   所以 P1/P2 实际测到的是**提示词开销**，不是算法。

2. **差异被"第几次尝试成功"的运气完全淹没。** 同一题在三个非强制阶段之间的极差：
   a1 22s、b2 64s、a4 81s、b1 157s。b1 一个题的波动就大于任何可能的插件效应。
   b1 的 235→78s 是两个 agent 选了不同技术路线：P0 的 agent 先撞上
   "system() 的 1.2KB 栈帧越过 4KB bss 页撞进只读 RELRO 段"这个坑，改用栈迁移 + execve；
   P1 的 agent 一发 ret2dlresolve 就通了。是路径差异，不是插件功劳。

3. **强制调用后机制确实生效，且 agent 认为它改变了行为。** P3 的 4 次调用抓到 6 个空洞。
   两个 agent 都报告：第一次调用的 `EXPAND` 裁决让它们**先去做实证验证，而不是直接写 payload**，
   因此都是一发命中。但这只是自述因果，n=1，无法与"本来就会这么做"区分。

4. **成本是确定的，收益不确定。** 协议段 1973 字符（≈500 token），**每一个模型请求**都要付，
   与任务长短无关；一次解题 20–50 个请求，即 1–2.5 万 token 的净开销。

**一句话**：在这类"单点漏洞 + 短推理链"的 pwn 题上，这个插件只有成本没有收益；
它的价值假设（拦住未被证实的中间断言）在 4 个单元以下的链上根本走不到。

## 5. 如果要继续测

- **换任务族**：需要多阶段假设链的活儿才可能吃到收益 —— 堆 feng shui 的多步利用链、
  逆向里的假设-验证循环、代码审计的跨函数数据流。这些题在靶场里还有 4 个没动
  （a2、a3、b3、b4 已部署在 10002/10003/10007/10008）。
- **改触发条件**：把协议里的"链长 > 4 单元"换成"每次失败的利用尝试之后必须调用"。
  P3 用的就是这个触发点，两个 agent 都照做了，说明这个改法在工程上可行。
- **改指标**：不要用秒。用"首次成功前的失败尝试次数"或"达到成功所需的总工具调用数"，
  这两个指标不受网速、思考长度、路径选择的影响，方差小得多。
- **加重复**：n ≥ 5 每格。以 b1 现在 157s 的极差，n=1 只能看到 150s 以上的效应。

# 第二轮：自建长链靶 + 换指标 + 加重复

第一轮的结论是"机制没触发"。这一轮按那三条建议重做。

## 7. 新靶：`s1` (chain v1)

现有 8 题里没有天然长链（b4 只是个 magic-word 反向题，a2/a3 是单点漏洞），所以自己写了一个：
`vm/chain.c`，静态编译，non-PIE，无 canary。

一条连接内 4 段依赖值，**任何一步错就断开重来**：

```
seed  随机、直接打印
A  = seed * 0x9e3779b9
B  = rol7(A) ^ 0x5a5a5a5a          ← rol 还是 ror，得从指令读
C  = table[i1] ^ table[i2]         ← 表打印出来，索引基数是个坑
D  = rol7(B ^ C ^ 0x13371337)      → 写进 g_want
vuln(): read(0, buf[0x40], 0x190)  → 溢出，ret 进 win(rdi 必须等于 D)
```

`win` 比较 `edi == g_want` 才给 shell，所以"猜一个地址/猜一个偏移"这种没根据的断言会直接失败，
而不是像简单题那样试两次就中——这正是要测的东西。

建设中的两个坑（都会让题目不可解，已修）：
- 静态 glibc 2.39 **没有** `pop rdi; ret`。用 `__asm__ volatile("pop %%rdi; ret")` 在二进制里
  显式放了一个 `g_pop_rdi`（0x4019a5 是函数入口，真正的 gadget 在 0x4019ad，中间隔着 push rbp）。
  顺带成了一个自然的诱饵。
- 内联汇编里 `%` 必须转义成 `%%`，否则汇编器报 `operand number missing`。

参考解 `solve_chain.py` 已打通（本地 + 线上都拿到 root shell 和 flag），确认靶可解。
参考解与源码都放在 `/root/chain-ref/`（700），解题 agent 读不到。

## 8. 设计

- 条件：**关闭** vs **开启 + 强制调用**（第一轮证明了不强制就 0 调用）。
- 每条件 3 次重复，同一靶、同一 brief（开启档只多一段"必须用 xefg_frame 并按其裁决行动"）。
- 三个指标：**服务上实际尝试次数**（`run.sh` 每次调用写 attempts.log，客观计数）、
  **从 T0 到拿旗的墙钟秒数**、**解的可复现率**（同一份 exploit 重跑 N 次）。

## 9. 结果

| 条件 | rep | 尝试次数 | 拿旗耗时 | 可复现率 |
|---|---|---|---|---|
| 关闭 | r1o | 2 | 83s | 5/5 |
| 关闭 | r2o | 2 | 81s | 5/5 |
| 关闭 | r3o | 3 | 79s | 5/5 |
| 开启+强制 | r1n | 3 | **326s** | **12/19 (63%)** |
| 开启+强制 | r2n | **1** | 97s | 5/5 |
| 开启+强制 | r3n | **1** | 90s | 5/5 |
| **均值** | 关闭 | 2.33 | 81s | 3/3 全 100% |
| **均值** | 开启 | **1.67** | **171s** | 2/3 全 100%，1/3 = 63% |

`xefg_frame` 调用：关闭档 0 次，开启档 **6 次**，报出 7 个空洞。

## 10. 结论

**它把"试错"换成了"先验证"，attempts 降了，墙钟没降，而且没拦住真正该拦的那次。**

1. **尝试次数确实降了**（1.67 vs 2.33）。两个干净的开启档 rep 都是**一发命中**服务，agent
   自述是因为第一次调用就把 ROP/对齐/分支目标判成 EXPAND，于是先去 grep `.text` 字节、
   先在本地 dry run，而不是直接打线上。这和设计意图一致。

2. **墙钟反而变差**（171s vs 81s），全部由 r1n 的 326s 拖累。也就是：省下的几次服务尝试，
   被前置验证的时间吃掉了，还倒贴。*在 90 秒级的任务上，验证比试错贵。*

3. **最关键的一条：它没拦住 r1n 的错误前提。** r1n 得出"这个容器里 `system("/bin/sh")`
   永远拿不到 shell"这个**错误结论**（我的参考解和 r2n/r3n 都证明 shell 是好的），
   然后在这个假前提上搭了一套 `close(3)→open("/flag")→read→write` 的两级 .bss 栈迁移
   纯 syscall ROP。这套东西对时序敏感，**19 次重跑只成功 12 次（63%）**。
   它确实调用了 xefg_frame 三次，但那次 `EXPAND` 打在"close(3) 保证 fd 是 3"这个单元上，
   而**错误的前提本身没被列进 frames**——工具只能给模型摆上来的东西打分。
   这是 HOLE_CHAIN 失效模式的教科书案例：garbage in, garbage out。

4. 所以"谁最快"这一轮仍然没有干净的赢家，但比第一轮多了一条明确的方向：
   **只有当模型愿意把没验证的断言摆上来时，这个机制才起作用；它对"自信地错"无能为力**，
   而自信地错恰恰是最贵的错误。

## 11. 如果还要继续

- **把"未经确认的外部事实"变成强制字段**：让协议要求每个 frame 单元标 `verified: binary|service|assumed`，
  `assumed` 一律判 EXPAND。r1n 那种"system 不行"的断言就会被自动拦下——现在的 schema 没有这个维度，
  模型可以选择不把它写进来。
- **任务时长要够**：90 秒的任务上验证成本压过收益。要找的是 5–15 分钟的多阶段任务。
- **指标用可复现率，不要用秒**。可复现率是唯一在这一轮里分开了两个条件的指标
  （关闭 3/3 = 100%，开启 2/3 = 100% + 1/3 = 63%），而且它在物理上有意义：
  对一个错误前提做加固，产出的就是脆的利用。

# 第三轮：证据门（default-deny）的受控对照

第二轮的第 1 条建议被实现了：每个单元必须标 `verified: binary|service|assumed`，
**没标 / 标了未知值 / 标 assumed —— 一律判成空洞**，并且会顺着 `HOLE_CHAIN` 污染下游。
严格度是宿主配置（`evidenceGate: hole | warn | off`），不是模型输入。

实现全部在插件包内（`lib/index.js` 协议段与 schema、`lib/engine.js` 判定分支、客户端一个下拉框），
**DSH 本体一行未改**。测试从 19 增到 23 个引擎断言，加宿主 7 + no-op 5 共 35 个全过。

## 12. 设计

同一靶（`s1` chain v1）、同一份 brief（都强制调用 `xefg_frame`）、同一批时间窗，唯一差别是
`evidenceGate`：

- **A = `off`**：几何判定照旧，证据字段被忽略（等价于第二轮的行为）。
- **B = `hole`**：缺标/assumed 一律空洞。

各 3 次重复。指标：服务上实际尝试次数、拿旗墙钟、解的可复现率。

## 13. 结果

| 条件 | rep | 尝试 | 拿旗耗时 | 可复现率 |
|---|---|---|---|---|
| A `off` | g1 | 2 | 313s | 5/5 |
| A `off` | g2 | 4 | 182s | 5/5 |
| A `off` | g3 | 1 | 204s | 5/5 |
| **A 均值** | | **2.33** | **233s** | 3/3 全 100% |
| B `hole` | h1 | **1** | 63s | 5/5 |
| B `hole` | h2 | **1** | 73s | 5/5 |
| B `hole` | h3 | 2 | 90s | 5/5 |
| **B 均值** | | **1.33** | **75s** | 3/3 全 100% |

插件侧：条件 A 6 次调用、`assumed 6`；条件 B 6 次调用、`assumed 8`，其中 8 个假设被证据门
升级成空洞。

## 14. 结论

**这是三轮里第一次出现方向一致、区间不重叠的差异。**

- 尝试次数 2.33 → 1.33（−43%）。
- 墙钟 233s → 75s（−68%）。A 的取值区间 182–313s，B 是 63–90s，**两组完全不重叠**；
  6 个样本 3+3 的完全分离，单侧置换检验 p = 1/20 = 0.05。n=3 仍然小，但这是目前为止
  唯一站得住的信号。
- 六个解全部 5/5 可复现——第二轮那个 63% 的脆解没有再出现。

机制上是这么起作用的：这六次运行踩的坑**完全一样**（`do_system` 的 `movaps` 栈对齐、
pty 行规程要求 payload 以换行结尾、要等 `congrats.` 再发命令）。差别只在于——
条件 A 的 agent 把这些当"大概没问题"直接打服务，用失败去换信息（2、4 次尝试）；
条件 B 的 agent 被迫把它们标成 `assumed`，于是被证据门当场判成空洞并给出 GROUND，
只好先去 `objdump`/`strace` 里核实，然后一发命中。

换句话说：**证据门没有让模型更聪明，它只是把"猜"的代价从"打一次服务"提前到"写 payload 之前"。**
而这个提前量，在一条连接错一步就重来的靶上，值 158 秒。

## 15. 这一轮的诚实边界

1. **n=3。** 区间不重叠是强信号，但置换检验 p=0.05 只是踩线。要坐实需要 n≥6。
2. **两轮的 B 不能互相比较。** 第二轮"开启"（无门）是 1.67 次 / 171s，这一轮 B（有门）是
   1.33 次 / 75s，但那是不同批次、不同时长基线，跨批次方差明显（第二轮 A 等价条件下是 81s，
   这一轮 A 是 233s）。**只有同一轮内的 A/B 可比。**
3. **agent 的自述不可信。** 条件 A 有一个 agent 报告"GROUND 列表指出了未落地的对齐"，
   但条件 A 的 gate 是 `off`，根本不会产出 GROUND 指令——它把 EXPAND 指令里的
   "ground these units" 记成了 GROUND 裁决。agent 对自己因果的叙述是加工过的，
   只有 `attempts.log` 和 flag 复验是硬的。
4. **仍然堵不住撒谎。** 模型完全可以标 `verified: "binary"` 而没查过。这一轮没有出现这种情况
   （八个 assumed 都是诚实标注的），但那是这次模型的诚实，不是机制保证。
   要抓只能抽样审计。

# 第四轮：措辞能提高采用率吗？

第三轮的结论依赖一个隐含前提：**工具被调用了**。但那个"调用"是我在 brief 里强制要求的。
三轮实测里，只要不要求，调用数就是 0。这一轮专门测这一件事。

## 16. 协议热更新

先把改措辞的成本降到零：协议正文从模块常量改成 state 字段，`systemPrompt.section` 的
`text` 本来就每次装配求值，所以 POST 一次即生效，**不用重装重启**。

```
POST /xefg-think/state {"protocol": "<正文>"}    # 下一个模型请求生效
POST /xefg-think/state {"protocol": ""}          # 回落内置
```

实测 1424 → 2761 → 1424 字符切换全部即时生效。顺带发现 PowerShell 5.1 的 `ConvertTo-Json`
会把长字符串序列化成 `{value,Count}`（437KB），改用 Node 直发才可靠。

## 17. 设计

同一靶、同一份 brief（**完全不提 `xefg_frame`**）、背靠背，各 3 次。唯一差别是协议正文：

- **V1（旧措辞，2761 字符）**：触发条件是"链长超过 4 个单元时调用"，定性是"建议"。
- **V2（新措辞，1424 字符）**：触发条件改为"写下任何依赖未观测值的 payload/脚本/文件之前必须调用"，
  定性改为"precondition, not advice"，并加了"an un-called chain is unfinished work"。

主指标是 **`stats.calls`**（前三轮不强制时恒为 0）。

## 18. 结果

| 条件 | rep | 尝试 | 拿旗耗时 | 可复现率 |
|---|---|---|---|---|
| V1 旧措辞 | v1a / v1b / v1c | 2 / 1 / 2 | 74s / 63s / 88s | 5/5 · 5/5 · 5/5 |
| **V1 均值** | | **1.67** | **75s** | 3/3 全 100% |
| V2 新措辞 | v2a / v2b / v2c | 2 / 2 / 2 | 71s / 94s / 151s | 5/5 · 5/5 · 5/5 |
| **V2 均值** | | **2.0** | **105s** | 3/3 全 100% |

**`xefg_frame` 调用次数：V1 = 0，V2 = 0。`assumed` 计数：两边都是 0。**

## 19. 结论：措辞不是问题，触发条件是

新措辞一个字都没改变采用率——**还是 0 次调用**。但读 agent 的自述会发现，
原因不是它们"懒得调"，而是**它们没有未落地的断言需要上报**：

- v2a：「VERIFICATION: all constants read from disassembly … the annotation about an 'index base
  trap' was NOT present in this build」——它把每个常量都从反汇编读出来了，还顺手证伪了
  我写进任务描述的一个陷阱。
- v2c：为了对齐问题，自己写 capstone 扫描证明二进制里 `pop rdi; ret` 数量为 0，再用
  `g_pop_rdi` 的 `push rbp; mov rbp,rsp; pop rdi` 绕过去。
- v1b：「spotting the custom symbols made the whole gate trivially reversible」——符号表直接把
  整个门禁摊开了。

也就是说：**协议写的触发条件是"你还没亲自观测过的东西"，而这些 agent 在写 payload 之前
就把所有东西都观测完了。规则没有没被遵守，只是从未被触发。**

第三轮为什么有 6 次调用？因为我在 brief 里**强制**了它。强制调用真正的效果不是"让工具分析"，
而是**逼模型把推理链外化到可以被打分的形式**。工具本身不分析任何东西——它只对摆上来的
单元打分；模型只要不自证，就没有单元被摆上来。

## 20. 最终定位

**这个插件的价值是"强制外化"，不是"自动自查"。**

- 它不能自我触发：不要求就不调用，措辞再怎么改也一样（第四轮）。
- 它不能自我验证：标 `binary` 而没查过，它看不出来（第三轮）。
- 它能做的只有一件事：**一旦模型被迫把链条写下来并标注证据，它就能精确指出哪一环是空的**
  ——第三轮 8 个 assumed 被升级成空洞，逼出前置验证，尝试次数 2.33→1.33、墙钟 233s→75s。

所以正确用法是**调度者/评测方的检查点**，不是模型的默认装备：派活时加一句"先把链条过一遍
`xefg_frame`，标 verified"，它才活；不加这一句，它就是一个占 1424 字符、每次请求都要付费的死重。

## 21. 配置决定

| 场景 | 开关 | 理由 |
|---|---|---|
| 日常问答、写代码、改文件 | **关** | 三轮实测 0 调用，纯付 ~360 token/请求 |
| 硬活（多步链、错一步重来）且你会要求它用 | **开，默认挡** | 第三轮实测 −68% 墙钟 |
| 硬活但不打算要求它用 | **关** | 第四轮实测：措辞改不动采用率 |

参数一律用默认（`evidenceGate: hole`、holeMax .25、tauFlow .45、β 6、严格模式关）。
另外从 v0.1.4 起，**激活状态不跨重启**：`enabled` 仍写盘供 UI 记忆，但加载时一律置 false，
每次启动都是关的。
